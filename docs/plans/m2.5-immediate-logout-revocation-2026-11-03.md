# M2.5 — Thu hồi access token ngay khi đăng xuất — Implementation Plan

> **For agentic workers:** Use `superpowers:executing-plans` to implement the tasks below. Work directly on main in the existing checkout; no worktree.

**Goal:** Sau khi logout thành công, mọi access/refresh token của đúng session đó bị từ chối ở request mới, kể cả token vừa được refresh; phiên đăng nhập khác vẫn dùng được.

**Architecture:** Dùng `app.user_session` hiện có làm nguồn trạng thái, không cache kết quả active. Guard thường/optional/admin/feedback kiểm signature + claims + session ownership/revocation/expiry + user active. Logout dùng guard xác minh JWT riêng, rồi service xác minh ownership để giữ retry idempotent.

**Tech Stack:** NestJS 11, JWT HS256, Prisma/PostgreSQL, Jest/Supertest, Node 22.

**Spec:** Yêu cầu trực tiếp 2026-11-03: làm logout vô hiệu token rồi push trước khi viết plan các lỗi audit còn lại; mở rộng quyết định stateless cũ tại PROGRESS, dùng phần session-check của M2.3/B3 nhưng không triển khai email/password recovery.

## Quyết định và phạm vi

- Chủ dự án đã yêu cầu triển khai và push; không thêm bước xin duyệt lại.
- Giải pháp chọn: DB lookup theo PK session ở mỗi request có token. Blacklist Redis cần hạ tầng mới; chỉ xóa token FE không vô hiệu bản sao, nên không đáp ứng yêu cầu.
- Không xóa cứng user/session: đánh dấu `revoked_at`, giữ bằng chứng và khả năng retry. Backend không thể xóa localStorage của trình duyệt từ xa; handoff chỉ rõ trách nhiệm FE.
- Không migration/dependency/env mới; JWT/session đang còn hiệu lực tiếp tục dùng được.
- Kiểm `typ=access`, `sub` bigint dương hợp lệ, `sid` UUID, `exp` hợp lệ và HS256 trước DB.
- Session không tồn tại, user không khớp, đã revoke/hết hạn, user không active → 401 `AUTH_TOKEN_INVALID`.
- DB lỗi trong session guard → 503 `AUTH_SERVICE_UNAVAILABLE`, không coi là anonymous/token sai, không tự cho qua.
- API public không token tiếp tục guest; có token revoke phải 401.
- Logout lặp với cùng JWT chưa hết hạn → 200 cùng id/revoked_at; token hết hạn/sai chữ ký → 401.
- Thay đổi áp dụng request đi qua guard sau revocation; không hứa hủy request/SSE đã qua guard trước đó. FE cần abort luồng đang chạy.
- Admin vẫn kiểm role từ DB. Feedback vẫn áp user quota sau auth.
- Có thể thêm một query/session mỗi request (admin giữ thêm query role); chưa tối ưu bằng cache vì sẽ mở lại cửa sổ thu hồi.

## Review Focus

5. Phiên khác và user khác không bị revoke → task 3 HTTP isolation/ownership.
